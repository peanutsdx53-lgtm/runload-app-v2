# UI/UX改修の実画面・スクリーンショット受入ゲート
最終更新: 2026-11-02
対象: RunLoad v2 の全UI/UX改修。研究理論・科学的意味・正式Currentには変更を加えない。

## ユーザー承認済みの運用規則（2026-11-02）
- コード修正・自動テスト成功・スクリーンショットの自動生成 **だけでは完了ではない**。
- 更新後の **実アプリ** を操作して得たPC・スマートフォンのスクリーンショットを担当者が実際に閲覧し、意図した改善が再現されているか確認する。
- 修正対象だけでなく周辺画面、他の表示状態、画面遷移、操作、レスポンシブ配置、以前正常だった機能も確認する。新しい不具合があれば再修正する。
- 再修正ごとに **最新の修正コミットで再撮影** → 目視分析 → 動作・回帰テストを行い、問題が解消したことを確かめる。
- 未確認のスクリーンショット、旧コミットのスクリーンショット、部品単体のデモを「最新実アプリの目視PASS」の証拠に転用しない。
- 自動テスト成功と、人間の実画面目視確認、iOS/Android実機確認は**それぞれ別のゲート**として記録する。対象の実機が使えない場合は「未実施」。
- 画面検証を実行できない、または欠陥が残る場合は **未完了（未PASS）** として記録し、完成数・PASS数に含めない。

## 画面ごとの受入チェック
1. **実装と根拠**：変更前後の差分と、機能設計根拠・画面設計根拠を区別。研究成果の効果を実証済みと断定しない。
2. **最新の実画面**：SHA、ブラウザ名、デバイス幅（原則320/390/1440px）、URL・画面、テストデータ／操作シナリオ、画像ファイルを特定する。ChromiumとWebKitの差異も必要に応じて調べる。
3. **目視評価**：文字のサイズ・行間・コントラスト、折返し、はみ出し、切れ、重なり、余白、コンテンツ優先順位、ボタンの並び／タップ領域、固定ナビ・スクロール時の重なり。画面だけでなく状態通知が事実と一致するか確認する。
4. **状態・反例**：未入力、入力途中、入力済み、保存後、編集・削除後、エラー、長文、数値0、無効値、条件外の科学的参考値、遷移・再訪時を該当画面ごとに選ぶ。S09は科学的比較が可能・不可の両方、3タブ維持。
5. **回帰・周辺検査**：関連画面・遷移と、本来変更していない既存機能を操作。最新SHAの自動テスト・スクリーンショット撮影結果も確認する。
6. **不具合修正ループ**：目視で問題が見つかれば不合格として記録し、変更を行い、新SHAで1〜5をやり直す。単に再テストの実行を依頼するだけで完了にしない。
7. **記録と判定**：修正理由（機能／画面）、受入画像、見つかった問題と対処、テスト結果、未確認範囲を残す。全受入条件を満たした場合のみ「画面PASS」。科学・成立条件・リリース全体のPASSと区別する。
