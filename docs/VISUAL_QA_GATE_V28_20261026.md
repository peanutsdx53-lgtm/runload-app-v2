# RunLoad：画面改修ごとのスクリーンショット品質ゲート（Ver.28）

作成：2026-10-26。対象：今後の `runload-app-v2` UI改修。正式研究Current、科学仕様、保存契約は変更しない。

## 背景

Ver.27「距離・時間・ペース」では、Chromiumのスクリーンショットが正常でもiPhoneのWebKit系画面で長文がカード外にはみ出した。画面全体の横スクロール量の検査だけでは、`overflow:hidden`によるカード内の文字欠けを検知できなかった。

## 以後の必須工程

1. **改修前確認**：該当画面のスクリーンショットを保存し、再現手順、画面幅、記録状態（なし／保存あり／失敗）を特定する。
2. **改修・境界確認**：科学計算／保存データ／参考文献などの未承認仕様を変更せず、利用できる機能として接続する。
3. **自動QA＋撮影**：少なくとも PC 1440px、スマホ390px、狭幅320px、広めのスマホ430pxで撮影。変更された画面について、必要なら375px・768px・1024pxも追加。iPhoneの表示に影響する場合はWebKitでも撮影する。
4. **画像の目視検査**：改修した画面をスクリーンショットで実際に確認する。画面端の欠け、文字の重なり、カードのはみ出し、意図しない空白、情報の階層、ボタンの視認性、下部ナビとの干渉、配色の一貫性を点検する。スクリーンショットの撮影だけで合格としない。
5. **要素内部の寸法QA**：`document.scrollWidth`に加えて、文章・ボタン・カードの実際の矩形、テキストフラグメントの右端、内部`scrollWidth`、上下の重なりを確認する。意図された横スクロール（テーマチップ等）は独立して判定する。
6. **反復改修**：欠け・視認性不足・崩れがあれば合格扱いせずCSS／文言／レイアウトを修正して、再度撮影・検査する。CSSで単に隠したり`overflow:hidden`を足すだけの回避は禁止。
7. **統合前後の確認**：Node全回帰と該当画面のブラウザー検証がPASSした後で`main`に統合し、公開GitHub Pagesでも実際のHTML/JS/CSSと操作を確認する。iOS Safari実機で未検証の内容は未検証と明記する。
8. **記録**：各工程のコミット、テスト件数、GitHub Actions URL、代表スクリーンショットと残存限界を改修記録へ記載する。

## Ver.28の重点検査

- 探究「距離・時間・ペース」の日本語見出し・説明・保存済み走行カード・振り返りCTA。
- **記録なし／正式手入力走行あり**の双方で表示確認。
- Chromium 4サイズとWebKitのスマホ系サイズで、カードの文章や枠線が右側に切れず自然に改行されること。
- 原因は日本語の改行規則とCSS Gridの最小コンテンツ幅の相互作用が疑われる。テスト上のPASSはiPhoneの実機Safari全条件の保証とは同一ではない。

この品質ゲートは以後の未実装画面開発でも継承し、装飾の優先順位を未実装機能より高くしない。ただし**新規実装の完了条件に視覚品質の確認を必ず含める**。
